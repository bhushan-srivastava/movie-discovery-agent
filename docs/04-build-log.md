## Real-Environment Connectivity Investigation and Fixes

Date: 2026-08-01

### Context

`docs/05-test-report.md` previously recorded real Neon/Gemini/Neon MCP smoke testing as **BLOCKED** after an "UnknownHost" failure. A follow-up investigation re-tested real connectivity (DNS, TCP, and live API calls) against Neon Postgres, Neon MCP, and the Gemini API. DNS/TCP connectivity to all three hosts succeeded; the previously reported failure did not reproduce. Instead, three separate, real, fixable issues were found and corrected.

### Defect 1 — Deprecated Gemini model

**Symptom:** real backend startup with development credentials produced `com.google.genai.errors.ClientException: 404 ... This model models/gemini-2.5-flash is no longer available to new users`.

**Root cause:** `gemini-2.5-flash` is no longer served to this API key; `gemini-2.0-flash` returns HTTP 429 (zero free-tier quota). `gemini-flash-latest` (resolves to `gemini-3.6-flash` at time of testing) returns HTTP 200.

**Fix:** `backend/src/main/resources/application-development.properties` default changed from `${GEMINI_MODEL:gemini-2.5-flash}` to `${GEMINI_MODEL:gemini-flash-latest}`.

**Verification:** real streaming chat request returned HTTP 200 with `text-delta`/`completion` NDJSON events; assistant message persisted to real Neon only after successful completion.

### Defect 2 — Neon MCP client library forces a duplicate `/mcp` path

**Symptom:** with `spring.ai.mcp.client.enabled=true` and `NEON_MCP_URL` set to a full address (for example `https://mcp.neon.tech/mcp?readonly=true`), backend startup failed with `404 Not Found from POST https://mcp.neon.tech/mcp/mcp`.

**Root cause:** Spring AI's `WebClientStreamableHttpTransport` always appends its own `endpoint` (default `/mcp`) to the configured `url`. When `url` already ends in `/mcp...`, the library produces a duplicated `/mcp/mcp` path.

**Fix:** `backend/src/main/resources/application-development.properties` sets `spring.ai.mcp.client.streamable-http.connections.neon-mcp.endpoint=#neon-mcp`. A fragment-only reference (`#...`) is a same-document reference per RFC 3986 §5.3: it leaves the base `url`'s path and query completely untouched (fragments are stripped client-side before any HTTP request is sent). This lets `NEON_MCP_URL` remain one single, complete, unmodified address — including its own `readonly=true` restriction — with no code-side URL surgery required.

**Verification:** live MCP `tools/list` succeeded (JSON-RPC handshake with `mcp-server-neon`); no 404.

### Defect 3 (security-relevant, corrected before any write-capable use) — `category` filter silently removed real query capability

**Symptom:** `NEON_MCP_URL` originally included `&category=schema,querying,data_api,observability,docs`. With this value, Neon's MCP server returned only 2 generic tools (`search`, `fetch` — project/org search only, no movie-table access).

**Root cause:** the category values used are not recognized by the live Neon MCP server's category taxonomy, so the filter matched nothing meaningful and the server fell back to its unfiltered generic tools.

**Fix:** `category` param removed from `NEON_MCP_URL`; only `readonly=true` retained.

**Verification (real server, no mutation performed):** live `tools/list` returned 22 tools. Neon's server embedded this explicit confirmation in every tool description: *"The MCP server is currently configured with read-only permissions. All write-access tools have been removed. All remaining tools are limited to read-only operations (for example, read-only SQL queries)."* Destructive/admin tools (`delete_project`, `create_project`, `delete_branch`, `provision_neon_auth`, `configure_neon_auth`, `prepare_database_migration`, etc.) were confirmed **absent**. This satisfies FR-9/FR-12/Criterion 10 (read-only, project-scoped Neon MCP access) against the real server, not only via system-prompt policy.

**Residual note:** `mcp.neon.tech` was observed to intermittently fail client-side initialization (timeout) under rapid repeated connection attempts during testing. This is external service behavior, not a defect in this repository; no code or config change was made for it.

### Defect 4 — Pre-stream chat timeout hardcoded too short for real tool-augmented calls

**Symptom:** real chat requests that required Gemini to reason over the full MCP tool schema set consistently returned HTTP 504 (`Model did not respond in time`), even on requests that were otherwise succeeding.

**Root cause:** `ChatStreamController` hardcoded the pre-stream `DeferredResult` timeout to `10_000L` (10s). A real Gemini + Neon MCP tool round-trip (MCP `request-timeout` alone is configured at 20s) plus model planning/generation latency routinely exceeds 10s.

**Fix:** timeout externalized per NFR-1 ("Model requests SHALL use a configurable timeout"):
- `backend/src/main/java/com/group/moviediscoveryagent/controller/ChatStreamController.java`: hardcoded `10_000L` replaced with `@Value("${app.chat.pre-stream-timeout-ms:45000}") long preStreamTimeoutMs`.
- `backend/src/main/resources/application.properties`: `app.chat.pre-stream-timeout-ms=45000` added as the common default.

**Verification:** `backend\mvnw.cmd clean package` — **BUILD SUCCESS**; **20 tests, 0 failures, 0 errors, 0 skipped** (mocked-`ChatClient` tests respond instantly and are unaffected by the timeout value). Confirmed no frontend/Vite client-side timeout is shorter than the new backend value (frontend `fetch()` in `chatApi.ts` uses no timeout/`AbortController` by default; Vite's dev proxy has no timeout override).

- `backend/src/main/resources/application.properties` (new `app.chat.pre-stream-timeout-ms` property)

### Known Limitations (updated)

- Neon's hosted MCP endpoint (`mcp.neon.tech`) exhibits intermittent client-initialization timeouts under rapid repeated connections; this is external service behavior outside this repository's control.
- Spring AI 2.0 does not expose reliable tool-start/tool-result lifecycle callbacks (previously documented); real tool invocation during a live chat turn can only be confirmed via MCP-level JSON-RPC logs, not application-level event types.

### Defect 5 — No explicit catch-all exception handler (NFR-2 hardening)

**Symptom:** `RestExceptionHandler` (`@RestControllerAdvice`) only mapped `NotFoundException`. Any other uncaught `RuntimeException` from a non-streaming controller (for example a transient database error) would fall through to Spring Boot's default `BasicErrorController`. Spring Boot's own defaults (`server.error.include-message`/`include-stacktrace` = `never`) already prevent leaking exception messages or stack traces, so this was not an active data-exposure defect, but NFR-2 compliance was **incidental** (dependent on framework defaults never being changed) rather than **explicit**.

**Fix:** added `@ExceptionHandler(Exception.class)` to `RestExceptionHandler` that logs the real exception server-side only and always returns a fixed, generic `{"status":500,"error":"Internal Server Error","message":"An unexpected error occurred"}` body, regardless of future `server.error.*` configuration changes.

**Verification:** `backend\mvnw.cmd clean package` — **BUILD SUCCESS**; **20 tests, 0 failures, 0 errors, 0 skipped** (existing 404/400 tests still pass — `NotFoundException` remains matched by the more specific handler).

### Remaining Limitation Not Addressed This Session (flagged for a decision, not silently changed)

**MCP query guardrails (FR-12) are enforced only via the `MovieAssistantPrompt` system-prompt text** (`backend/src/main/java/com/group/moviediscoveryagent/chat/MovieAssistantPrompt.java`): SELECT-only intent, `movie`-table-only scope, and the 5-row limit are instructions to the LLM, with **no code-level interception** of the actual tool-call arguments or tool results to verify or enforce them. Two independent layers currently reduce real-world risk:
1. Neon MCP is configured `readonly=true` at the server (Defect 3 above), so no mutation is possible even if the model ever attempted one.
2. The `movie` table is the only application-relevant table with real data; there is no code path exposing `conversation`/`message` table contents through MCP.

However, a model could still (in principle) request more than 5 rows or read outside the `movie` table read-only, since nothing in Java validates the SQL text or truncates results before they reach the user. Adding code-level enforcement (intercepting `run_sql` tool-call arguments/results) is a real, scoped enhancement, not implemented in this session because it changes the MCP tool-calling pipeline and was not part of the current fix request — flagged here for an explicit decision rather than silently expanded.

## Story 5 Build Fix — Production Defects (Historical, Superseded by Markdown Migration)

> Historical note: this section records the earlier HTML-contract implementation. The final implementation below supersedes the HTML response contract with Markdown and ReactMarkdown rendering.

Date: 2026-08-01

### Context

Manual UI testing revealed two unresolved production defects:
1. One user request displays the same assistant response twice (duplicate rendering).
2. New assistant responses contain literal Markdown markers such as `**` instead of clean HTML.

### Root Cause Analysis

**Defect 1 — Duplicate Rendering:**
- `ChatPage.handleSend()` called `stream.startStream()` to accumulate text in `assistantText`, then `getMessages()` to reload persisted messages.
- However, `stream.reset()` was not called after persisted reload, leaving `assistantText` still truthy.
- `ChatTranscript` rendered both the persisted message AND a temporary streaming card (checked `isStreaming || Boolean(streamingText)`).
- Result: two identical cards visible simultaneously.

**Defect 2 — Markdown Visible:**
- `MovieAssistantPrompt.SYSTEM_PROMPT` contained only a vague instruction: `"Do not return markdown, return html..."`.
- The system prompt was **never passed to the ChatClient request** — `ChatOrchestrationService.streamAssistantResponse()` called `chatClient.prompt()` but never `.system(MovieAssistantPrompt.SYSTEM_PROMPT)`.
- `ChatTranscript.tsx` had no HTML sanitization; it rendered raw assistant content as plain text, so any Markdown from the model appeared unchanged.
- Result: model responses contained literal `**`, `*`, `#`, backticks despite the vague prompt instruction.

### Fixes Applied

**Fix 1A — Clear Streaming State After Persisted Reload:**
- Modified `ChatPage.handleSend()` to call `stream.reset()` after `setMessages(await getMessages(...))`.
- This clears `assistantText` and all temporary streaming state once persisted messages are reloaded.
- Result: exactly one assistant card remains visible.

**Fix 1B — Improve Streaming Render Logic:**
- Modified `ChatTranscript.tsx` to only show streaming message if `isStreaming && streamingText.length > 0`.
- Previously: `isStreaming || Boolean(streamingText)` (shows card if either is true, even after completion).
- Now: both must be true, so streaming card disappears once `isStreaming` becomes false.

**Fix 2A — Replace System Prompt with Strict HTML Contract:**
- Rewrote `MovieAssistantPrompt.SYSTEM_PROMPT` from 5 lines to 30+ lines with explicit sections:
  - **RESPONSE FORMAT:** Lists only allowed HTML elements (p, strong, em, ul, ol, li, br) and forbids attributes.
  - **CRITICAL: DO NOT USE MARKDOWN SYNTAX:** Lists all prohibited Markdown markers explicitly (**, *, #, backticks, fences).
  - **PROHIBITED ELEMENTS:** Lists elements that must not be returned (script, style, iframe, form, svg, link, image).
  - **PROHIBITED ATTRIBUTES & CONTENT:** Forbids HTML attributes, CSS, classes, IDs, event handlers, href, src, javascript/data URLs.
  - **ALLOWED MOVIE FIELDS:** Lists queryable columns.
  - **IMPORTANT COLUMN NAMES:** Specifies actual Neon names (original_language, runtime_minutes).
  - **DATA ACCESS:** Forbids accessing conversation/message tables; forbids revealing SQL/schema/credentials.
  - **NO HARD-CODED FIVE-RESULT LIMIT:** Removed and replaced with "Return the number requested by the user. If no number is specified, return a concise list."

**Fix 2B — Pass System Prompt to ChatClient Request:**
- Modified `ChatOrchestrationService.streamAssistantResponse()` to call `.system(MovieAssistantPrompt.SYSTEM_PROMPT)` immediately after `chatClient.prompt()`.
- Result: the model now receives the explicit HTML contract and Markdown prohibition.

**Fix 2C — Sanitize HTML Output with DOMPurify:**
- Modified `ChatTranscript.tsx` to:
  - Import `dompurify` (v3.0.6, added to `frontend/package.json`).
  - Create `sanitizeConfig` whitelist: `ALLOWED_TAGS: ['p', 'strong', 'em', 'ul', 'ol', 'li', 'br']`, `ALLOWED_ATTR: []`.
  - Create `sanitizeHtml()` function using `DOMPurify.sanitize(html, sanitizeConfig)`.
  - Create `renderAssistantContent()` that renders sanitized HTML via `dangerouslySetInnerHTML`.
  - Render user messages as plain text; render assistant messages via `renderAssistantContent()`.
- Result: any HTML returned by the model is sanitized. Script, style, event handlers, links, images, forms, and all attributes are stripped. Only clean, approved HTML remains.

### Draft Mode Flow

1. **New button clicked:** No HTTP call. `isDraft=true`, `selectedId=null`, composer focused.
2. **User submits first message:** Trim input, validate non-blank, truncate to 255 chars, call `POST /api/conversations` with title, store returned ID, stream message.
3. **Subsequent messages:** No new conversation. Stream to existing ID.
4. **Creation failure:** Stay in draft mode, preserve typed message, show error.
5. **Streaming failure:** Keep created conversation, reload sidebar, show error.

### Markdown System Prompt

Replaced HTML contract with Markdown-focused contract:
- Requests clean Markdown with paragraphs, lists, bold, italic
- Prohibits raw HTML, scripts, styles, iframes, forms, images
- Specifies actual Neon column names
- No hard-coded five-result limit
- Requires Neon MCP for queries
- Prohibits SQL/schema/credentials exposure

### Markdown Rendering (Frontend)

- **Assistant messages:** `ReactMarkdown` with `remark-gfm` plugin
- **User messages:** Plain text only
- **Links:** Text rendered, no clickable href
- **Images:** Ignored (custom renderer returns null)
- **Streaming:** Progressive accumulation of Markdown deltas
- **Removed:** `dangerouslySetInnerHTML`, DOMPurify, HTML sanitization
